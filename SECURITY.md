# Authentication and API security milestone

PostgreSQL is now required by the running API. Accounts, Argon2id password hashes, hashed sessions, permissions, monthly quota reservations, generation jobs, usage records, and audit records use the existing Drizzle schema. JSON personnel and browser state are never authentication sources.

## Setup

1. Install dependencies with `npm ci` and configure a private `DATABASE_URL` in server runtime configuration.
2. Run `npm run db:migrate` against that database. The new migration adds shared authentication throttle counters.
3. Run `npm run admin:provision` from a trusted interactive server terminal. Enter the first administrator's email, name, and password. Password input is hidden and never passed in command arguments. The command refuses to run when an administrator exists.
4. Start locally with `npm run dev`, or build with `npm run build` and run `NODE_ENV=production npm start`.
5. For production set `APP_URL=https://your-studio.example` and use HTTPS termination. Set `TRUST_PROXY=1` only when exactly one trusted reverse proxy strips incoming forwarding headers and the app port is inaccessible directly. Use verified database TLS (`DATABASE_SSL_MODE=verify-full`) and your database provider's trusted CA configuration.
6. Sign in as admin. Give each approved member a finite quota and enable API access. These checks also apply to administrators. New registrations and admin-created members are always `USER`, with zero quota and API access disabled. This milestone leaves self-registration open for unprivileged accounts; restrict it operationally if your workspace requires closed enrollment.

Provider keys belong only in server environment variables. Do not use `VITE_` names, public configuration files, or frontend build substitutions. The backend bundle is `build/server.cjs`; only the frontend `dist/assets` and `dist/index.html` are published. Production runs reject HTTP. Development's Vite file server denies backend, credentials, runtime data, and build paths.

## Private storage and migration

`DATA_DIR` defaults to `./private-data`; `UPLOADS_DIR` defaults to `./uploads` or an existing `/app/uploads` mount. Use separate persistent private mounts. Configuration fails if private data overlaps uploads or frontend public directories, including through existing symlinks. Uploads are served through authenticated ownership checks, not static directory hosting. `/uploads/data/*` and all non-image paths are denied.

Before switching an existing deployment, retain an offline copy of its JSON data and move content files out of `/app/uploads/data`. Do not configure that old directory as `DATA_DIR`. Legacy JSON user roles are deliberately not imported into PostgreSQL. Create real accounts and assign privileges through the protected admin API. Legacy assets without an authoritative `ownerUserId` are hidden; map them to verified PostgreSQL users as an explicit migration. Do not derive owners or admins automatically from legacy emails.

Web backup exports contain allowlisted templates and asset metadata only. They omit accounts, password hashes, sessions, tokens, settings, quotas, audit logs, and provider configuration; known runtime secrets are redacted. Restore rejects account fields and validates all content before writing. Asset owners must already exist in PostgreSQL, and local image ownership must match. Back up PostgreSQL and the private image mount separately with restricted access. Database backups inherently contain sensitive authentication records; this API does not export them.

Templates remain in the private JSON content store for this milestone. `isPublic=true` permits authenticated users to view them; other templates require admin. Templates requiring approval can only be generated by admins. Assets and jobs are owner-only, including their image downloads. JSON content storage supports one application writer; accounts and quota concurrency use PostgreSQL across processes. Move content and image-owner metadata to PostgreSQL/object storage before running multiple application instances.

## Session and quota behavior

Session cookies are HttpOnly and SameSite=Strict; production uses Secure, a `__Host-` name, and no Domain attribute. Sessions have an 8-hour idle and 24-hour absolute lifetime. Mutations require JSON, origin checks, and a session-derived CSRF token held only in application memory. Login and registration attempts share PostgreSQL counters (30 per IP and 10 per email per 15-minute window).

Logout revokes the active session. Password changes, suspension, and role/API-permission changes revoke all account sessions and increment the session version. Every request checks current account state, session version, expiry, and revocation. Password change is available in Profile. New accounts use passwords of at least 12 characters. Admin MFA and secure account activation/recovery are follow-up work; existing recovery-token tables are not exposed as a pretend recovery flow.

Image generation and prompt optimization each reserve one quota unit in a transaction before contacting a provider. A conditional update prevents oversubscription; job settlement and ledger entries are idempotent. The month is measured in UTC. Provider models are selected by server configuration. No provider fallback creates a second unaccounted call. Dispatched failures consume a unit because upstream cost may already have occurred. A process crash leaves its unit reserved and fails closed; reconcile stalled jobs before releasing reservations. Admin resets preserve outstanding reservations. Missing provider credentials return 503 rather than a simulated successful image.

## Validation

`npm run check` runs types, lint, tests, build, and secret scanning. The security suite starts a real isolated temporary PostgreSQL instance and tests credential verification, forged roles/browser state, 401/403 route protection, CSRF, expiry, logout/suspension/password/permission revocation, private assets/jobs, concurrent quota reservations, sanitized errors/backups, and production cookies/HTTPS. Provider calls use test doubles; no quota is spent during tests. An optional `TEST_DATABASE_URL` must identify a disposable database distinct from the runtime database. `npm run security:scan` scans source and frontend output without printing suspected credential values.

This milestone does not complete mandatory admin MFA, secure recovery/activation delivery, a durable generation worker with reconciliation, or a full PostgreSQL migration for content. Those remain necessary before describing the whole deployment as fully hardened.
